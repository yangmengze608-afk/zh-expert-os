## S2 — Router Native Invocation / Identity Contract

在**当前 WorkBuddy lead/main context** 中真实调用：

`subagent_type = zeos-router`

Lead 分配：

```text
ZEOS_TASK_ID: smoke-router-001
ZEOS_ARTIFACT_NAMESPACE: /tmp/zeos-v05-smoke/router
```

自包含任务：

> 这是 release smoke，不是真实业务。请为“给现有 Web 应用设计用户数据导入流程并验证导入数据质量”生成最小 Capability Map。不要读取文件，不需要生成 artifact。严格按你的 ZEOS_ENVELOPE 契约回传。

必须记录：

- WorkBuddy 返回的真实 `host_task_id`
- `subagent_type`
- terminal host status
- worker 最终原文
- worker envelope 的 `task_id`

**成功条件：**

- 真实 invocation 存在；
- `host_task_id` 由 WorkBuddy 控制面返回；
- envelope `task_id == smoke-router-001`；
- 不要求、也不允许 child 猜 host_task_id；
- host_task_id 与 assignment id 在报告中是两个独立字段。

把 worker 最终原文保存到：

`/tmp/zeos-v05-smoke/router-output.txt`

然后真实运行：

```bash
zh-expert-os workbuddy-validate-envelope \
  --file /tmp/zeos-v05-smoke/router-output.txt \
  --assignment-id smoke-router-001 \
  --agent-id zeos-router \
  --host-task-id <REAL_HOST_TASK_ID> \
  --host-status completed
```

保存 CLI 原始 JSON 返回。

## S3 — Evidence Worker / Artifact Provenance

真实调用：

`subagent_type = zeos-evidence`

Lead 分配：

```text
ZEOS_TASK_ID: smoke-evidence-001
ZEOS_ARTIFACT_NAMESPACE: /tmp/zeos-v05-smoke/evidence
```

任务：

> 这是 release smoke。只在你的 namespace 内创建 `evidence.json`，内容必须包含 synthetic canary `ZEOS_V05_SMOKE_CANARY_71C9`。从真实文件计算 sha256。回传一个 claim：“evidence.json contains the assigned synthetic canary”，其 evidence 必须指向本 assignment 的真实 artifact，并在 artifacts[] 返回相对路径 `evidence.json` + sha256。严格按 ZEOS_ENVELOPE 返回。不要读取任何 sibling namespace。

Lead 必须：

1. 等 worker terminal；
2. 记录真实 host_task_id；
3. 保存 worker 原文到 `/tmp/zeos-v05-smoke/evidence-output.txt`；
4. 用 `workbuddy-validate-envelope` 校验；
5. lead **独立**读取 `/tmp/zeos-v05-smoke/evidence/evidence.json`；
6. lead **独立重算 sha256**；
7. 比较：
   - child envelope artifact sha
   - claim evidence artifact_sha256（若提供）
   - lead 重算 sha
8. 三者出现冲突时立即 FAIL，不做解释性补丁。

禁止人工手打 child 的 hash 到命令里做“旁证”。必须直接从原始 envelope / artifact machine-read。

## S4 — Registry → Native Expert Export

不要污染真实 `~/.workbuddy/agents/`。

在临时目录运行：

```bash
rm -rf /tmp/zeos-v05-smoke/export
mkdir -p /tmp/zeos-v05-smoke/export

zh-expert-os workbuddy-export-expert \
  --expert router \
  --output-dir /tmp/zeos-v05-smoke/export
```

核验：

- 生成 `router.md`
- 普通文件
- 有 `name: router`
- 有 `maxTurns: 200`（兼容元数据）
- 有 ZEOS_ENVELOPE 契约
- 没有把 Registry `source` / `license` 塞进执行 prompt
- 输出 JSON 明确 `native_hot_load_ready: true`
- 这不改变 Registry status

然后负面测试 candidate gate：

- 找一个真实 candidate；若 registry 当前没有 candidate，使用临时 Registry fixture / 单元测试结果，不要为了 smoke 修改正式 registry。
- candidate 不得被 `workbuddy-export-expert` 正常导出。

## S5 — Top-level Skill Discovery

检查当前 WorkBuddy 会话能否发现/加载：

`~/.workbuddy/skills/zh-expert-os/SKILL.md`

分三种结果记录：

- `HOT_DISCOVERED`：当前会话可直接加载；
- `RESTART_REQUIRED`：文件已正确安装，但当前会话不热发现，重启/新会话后才发现；
- `NOT_DISCOVERED`：新会话也无法识别，属于 release blocker。

**HOT_DISCOVERED 不是 v0.5-alpha1 merge 的必要条件；NOT_DISCOVERED 是 blocker。**

不要因为 Skill 未热发现，就把 native worker 的成功伪装成 Skill 成功。
