## Blocker 1 — Router host_task_id absence check 使用了错误字符串

报告 §C 记录：

- 真实 `host_task_id = agent-33894946df9e4929`
- 但用于证明“envelope 内不含 host task id”的检查写成：

```text
"39894946" in envelope_body == False
```

这里 `39894946` 与真实 host id 的前缀 `33894946` **不一致**。

因此这条负向检查当前不能支持：

> child 没有把真实 host_task_id 放进 envelope。

这不是 Runtime 功能失败，但属于 smoke 证据链错误，必须修正。

### 修正要求

不要人工重打 envelope。

直接从 B 层已归档的 router 原始 output / transcript 机器读取，并检查 **完整字符串**：

`agent-33894946df9e4929`

要求报告回填：

- exact full host_task_id search count；
- search source file / transcript record；
- 结果应为 0 才通过；
- 若非 0，记录真实位置并重新判断 contract。

保留原错误记录，追加 correction，不要静默覆盖。

## Blocker 2 — 文档推荐的 fresh-install 命令在真实 WorkBuddy 环境中实际失败

当前 README / Adapter 文档主安装路径使用：

```bash
python -m pip install -e . --no-build-isolation
```

Smoke §H.4 明确记录：在真实 WorkBuddy 5.6.2 托管 Python 中，该命令失败：

```text
BackendUnavailable: Cannot import 'setuptools.build_meta'
```

本轮后续成功依赖的是**机器上已经存在、指向本仓库的 editable CLI 安装**。

所以 smoke 实际验证的是：

> 已有可用 CLI 的机器上，WorkBuddy Adapter 安装与 Runtime smoke 成功。

它**没有验证**：

> 一个 fresh user 按 README 的主安装命令能成功安装 CLI。

这不能简单归为“与仓库无关”的环境问题，因为这是当前公开文档推荐给 WorkBuddy 用户的安装命令，而它在实际受测 WorkBuddy 环境失败。

### 修正要求

优先走最小路径：

1. 在同一 WorkBuddy 5.6.2 环境运行：
   `python -m pip install -e .`
   （去掉 `--no-build-isolation`，让 pyproject build-system 正常提供 setuptools）；
2. 记录 rc / 原始关键输出 / 实际 import path；
3. 若成功：
   - WorkBuddy 文档与 README 的推荐安装命令改为 `python -m pip install -e .`；
   - `--no-build-isolation` 仅作为“已确认本地已有 setuptools>=68 时”的可选高级路径，或直接删除；
4. 若仍失败：
   - 不要掩盖；把 Python build prerequisite 写成明确安装前置条件，并给出在受测 WorkBuddy 环境真实成功的 fresh-install 路径。

不要求重做 S1–S6，只补 **installation-path verification**。

## Skill Discovery 审计

`HOT_DISCOVERED` 的判定可以接受，但要限定语义：

- **YES**：当前会话可按名加载 `zh-expert-os`；

因此 v0.5-alpha1 用户体验应写成：

> 显式调用 / 按名加载可用；自动索引与自动触发不作为本版本保证。

这不是 blocker，但建议在 WorkBuddy README 中明确。

## 其他非阻塞项

### CLI contract error traceback

Smoke 发现 assignment mismatch / candidate gate 这类预期拒绝会输出完整 Python traceback。

退出码与拒绝语义正确，所以不阻塞 alpha1；建议 v0.5-alpha2 统一为结构化 JSON error + 非零退出码。

### Evidence parent_refs 仍是语法约束，不是完整图解析

当前 `derived.parent_refs` 只强制“非空字符串数组”，并没有在核心模型中验证这些 parent refs 一定解析到现存 EvidenceRef。

因此“machine provenance”目前是**结构化、可审计**，但还不是完整 referential-integrity evidence graph。记录为后续技术债，不阻塞 alpha1。
