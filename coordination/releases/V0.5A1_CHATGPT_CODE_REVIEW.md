## 结论

PR #9 的总体架构与 EXP-001 / EXP-002 的宿主证据边界一致，可以进入真实 WorkBuddy release smoke。

在代码复核中发现并已直接修正 4 类实现问题：

1. **Node schema 与 Python serializer 不自洽**
   - `WorkBuddyNodeState.to_dict()` 会输出 `terminal`；
   - 原 `workbuddy-node-state.schema.json` 未声明该字段且 `additionalProperties=false`。
   - 已补入 `terminal`，并把它与 host status 的 terminal/non-terminal 语义绑定。

2. **Node / Envelope agent identity 未在核心模型层绑定**
   - CLI 会单独检查 agent id，但直接使用 `WorkBuddyNodeState` 时原模型只校验 assignment id。
   - 已要求 `envelope.agent_id == node.agent_id`，避免 envelope 被错误绑定到另一个 host node。

3. **copy-based installer 对“同内容 symlink”存在漏洞**
   - 原预检会跟随同内容 symlink，并把它视为幂等安装；
   - 这与“已验证的是普通 user-level 文件、未验证 symlink discovery”的发布契约冲突。
   - installer 现在对 Skill / native agent 的预存 symlink 一律报冲突，不覆盖、不视为成功安装。

4. **ZEOS_ENVELOPE Python 校验不够类型严格**
   - 原实现对错误 container type、bool confidence、未知 evidence 字段等场景可能抛普通 Python 异常或意外接受。
   - 现已显式验证 claims/artifacts/open_questions/evidence ref 的容器与字段集合，并拒绝 bool confidence。

附带文档修正：README 已把“链接到 ~/.workbuddy/agents”改成“以普通文件安装到”。

## 架构边界复核

以下 PR #9 声明与实验支持一致：

- `lead → workers` 是保守默认，不是宿主硬限制；
- `TaskStop` 是主动生命周期闸门，但 stop 后必须等 terminal；
- cancelled child 不保证 final envelope；
- `SendMessage success:true` 不等于 consumed / ACKED；
- tested interface 不宣称 agent timeout 已打通；
- `maxTurns` 只作兼容元数据，不作预算控制；
- namespace 是工程纪律，不是安全 sandbox；
- user-level native Expert 可热加载，但可调用不等于晋升；
- evidence scalar 必须带 machine provenance pointer。
