# 知流项目：Claude Code 调用示例

将 Claude Code 打开在“知流”项目根目录后，可以直接粘贴下面这段。

```text
请使用 /zh-expert-os 作为本次任务的总调度层，直接接管当前“知流”项目并继续推进，不要只给规划。

项目背景：这是知乎黑客松项目。核心产品方向是“让用户看见自己正在接触的信息”：在知乎信息流上提供一个克制、真实的 Dashboard，让用户看到最近接触内容的主题分布、变化和信息集中度。另一个关键技术问题是：如何可靠判断一篇知乎内容的中心思想/主要讨论角度，避免把“社交焦虑”错误归到“女权”等不相关主题。知乎官方提供了 API / Skill / MCP 能力，项目需要尽量让核心价值与官方 API 紧密结合，而不是只做一个静态前端演示。

请按 Zh Expert OS 的方式工作：

1. 先完整读取当前仓库、README、现有代码、设计稿、TODO、API 接入情况和 Git 状态，保留已有成果，不要无理由重构。
2. 从“最终要提交一个能演示、能解释、与知乎 API 紧密结合的黑客松作品”这个原始目标出发，建立 Capability Map。
3. 先检查现有能力，只组最小充分专家团。优先考虑 Product / Zhihu API & NLP / UX / Frontend / Evaluation & Red Team；不是所有角色都必须存在。
4. 只有真的缺 Expert 时才启动招聘；如果缺的是 Skill、Tool、Knowledge 或 Workflow，就补对应能力，不要为了展示 Expert OS 而扩编。
5. 如果 Claude Code 当前环境支持真正的 subagent / 独立 agent context，请让关键 Expert 独立处理自己的子任务；不要把同一上下文里的角色扮演投票当作独立证据。
6. 对“中心思想识别”重点解决：
   - 一篇内容的 primary topic / central claim 到底是什么；
   - 多主题内容如何给 primary / secondary topic；
   - 如何避免只靠关键词产生误分类；
   - 如何利用知乎 API 返回的信息、正文、问题上下文、话题/标签或可用元数据增强判断；
   - 如何设计置信度、unknown / ambiguous 状态和可解释证据；
   - 如何构建最小 benchmark 验证分类真的有效。
7. 对 Dashboard 重点解决：
   - 用户最近接触信息的主题分布；
   - 信息集中度如何定义、计算和解释；
   - 时间变化趋势；
   - 不制造虚假的“信息茧房诊断”，而是把它设计成可解释的 exposure monitor；
   - UI 要接近真实知乎 Web 产品，深色、克制、现代，Dashboard 更宽、更窄，不做海报式视觉。
8. 优先做真正影响评审的核心链路：知乎内容/API → 中心思想识别 → 主题聚合 → concentration / trend → Dashboard 展示。不要先堆不必要功能。
9. 对每个关键假设做 Red Team：API 是否真的提供所需字段？主题分类是否会产生误导？集中度指标是否有统计意义？演示数据是否会被误当成真实用户数据？
10. 直接实施：修改需要的代码和文档，补最小测试/样例数据/运行说明。能运行就运行，能测试就测试。不要停在“建议下一步”。
11. 如果发现当前方案有明显更短、更稳、更能拿分的实现，允许调整，但必须说明为什么，并尽量复用现有工作。
12. 最后只给我一个简洁交付报告：
   - 你调用了哪些真实 Expert / subagent；
   - 做了哪些改动；
   - 当前核心链路是否跑通；
   - 哪些仍是 mock / 假数据；
   - 哪些知乎 API 能力已经真实接入；
   - 下一步最值得做的一件事。

重点：最终目标是把“知流”做成一个真实、可演示、技术逻辑站得住的知乎黑客松项目，不是展示 Expert OS 本身。
```

如果 Claude 没有自动识别 Skill，可以把第一句改成：

```text
/zh-expert-os 请直接接管当前知流项目……
```
